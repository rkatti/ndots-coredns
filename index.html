Field notes · Kubernetes · CoreDNS · ndots

One hostname in CoreDNS. Three changes. One very long week.

Every pod in a Kubernetes cluster needed to resolve a single hostname to an internal IP instead of its public one. Adding that entry to CoreDNS looked like a five-minute job. It wasn't — because the pods weren't using CoreDNS at all, and once they were, Kubernetes' default DNS settings made curl time out on the exact entry we'd just added.

Kubernetes · CoreDNS · ndots ~9 min read
01 — The ask

Make the cluster lie about one hostname

A large application running in a Kubernetes cluster needed to reach an external vendor endpoint. The catch: public DNS resolved that hostname to a public address, but traffic from this cluster had to egress through a specific internal VIP instead.

Call the hostname vendor-api.example.net and the VIP 10.20.30.40. Simple ask. Map one name to one address, cluster-wide.

It took most of a week, and two of my three attempts made things worse before they made them better.

02 — Wrong turn

hostAliases works, and that's the problem

The obvious first answer in Kubernetes is hostAliases in the pod spec. It writes an entry straight into the pod's /etc/hosts, it's trivially simple, and it does exactly what it says.

It also fails as a platform answer.

Why it was rejected

hostAliases is per-pod. Every application team needing this endpoint has to add an identical block to their Helm chart, keep it in sync, and remember it exists the day the VIP changes. Shipping a fix that requires N teams to each carry the same change forever isn't shipping a fix — it's distributing a liability.

The right layer was CoreDNS. One entry, and every pod in the cluster inherits it without knowing anything happened.

03 — Wrong turn

The fix took down the apps it was fixing

CoreDNS ships a hosts plugin that does precisely this. Placement matters — it goes after kubernetes and before forward, so a query hits your override before CoreDNS gives up and asks upstream:

.:53 {
    errors
    health {
        lameduck 10s
    }
    ready
    kubernetes cluster.local in-addr.arpa ip6.arpa {
        pods insecure
        fallthrough in-addr.arpa ip6.arpa
        ttl 30
    }
    prometheus 0.0.0.0:9153
    hosts {                                  # <- added
        10.20.30.40 vendor-api.example.net   # <- added
        fallthrough                          # <- added
    }                                        # <- added
    forward . /etc/resolv.conf
    cache 30
    loop
    reload
    loadbalance
}

And CoreDNS immediately began crash-looping. OOMKilled.

What that actually cost

This is the part that stops being an infrastructure inconvenience. CoreDNS restarting in a loop means DNS queries time out — and a timeout is five seconds, retried three times. Roughly fifteen seconds of dead air per lookup. Application pods that resolve dependencies during startup didn't survive that. My DNS fix took down the workloads it was meant to fix.

The deployment carried a 128Mi memory limit with the request set to the same value — the platform default, untouched for years because nobody had ever asked CoreDNS to do anything beyond kubernetes and forward. Zero headroom. One additional plugin was enough to tip it over. Raised to a 256Mi limit against a 128Mi request, and the pods stabilised.

Order matters more than you'd think

Raise the memory as its own change, confirm it's applied, then add the plugin. If you ship both together and CoreDNS falls over, you've got two variables and no way to tell which one bit you. Verify the limit is actually live before touching the Corefile — a patch that silently didn't apply looks identical to a patch that didn't help.

# CoreDNS deployment — the headroom that was missing
resources:
  limits:
    memory: 256Mi   # was 128Mi
  requests:
    memory: 128Mi   # was 128Mi — same as the limit, zero headroom

Do not omit fallthrough

Without it, the hosts plugin becomes authoritative for every query it sees — returning NXDOMAIN for anything not in its list instead of passing the query down to kubernetes and forward. You will take out all DNS in the cluster in a single apply.

04 — The mystery

One tool resolved it. The other didn't.

CoreDNS healthy. Hosts entry loaded. From inside an application pod:

$ nslookup vendor-api.example.net
Name:    vendor-api.example.net
Address: 10.20.30.40          # correct

$ curl -v https://vendor-api.example.net
... hangs, then fails

Same pod. Same hostname. Same second. The thing that finally cracked it was close to an accident — trying the name with a trailing dot:

$ curl -v https://vendor-api.example.net.
... connects instantly

A trailing dot makes a hostname fully qualified. Which meant the problem was never resolution at all. It was everything the resolver was doing before it got around to trying the name I actually typed.

05 — The cause

ndots:5 is a tax on every external lookup

Open /etc/resolv.conf in any default Kubernetes pod and you'll find this:

nameserver 10.43.0.10
search my-namespace.svc.cluster.local svc.cluster.local cluster.local
options ndots:5

ndots:5 means: if the hostname contains fewer than 5 dots, treat it as relative first — append each search domain in turn and try those before trying the name as written.

Kubernetes sets this deliberately. It's what makes curl http://my-service work from inside a cluster, and it's a genuinely good default for internal traffic. But vendor-api.example.net has two dots. Two is fewer than five.

Resolver path · vendor-api.example.net
options ndots:
1vendor-api.example.net.my-namespace.svc.cluster.localNXDOMAIN
2vendor-api.example.net.svc.cluster.localNXDOMAIN
3vendor-api.example.net.cluster.localNXDOMAIN
4vendor-api.example.net.10.20.30.40

4 queries to answer one lookup. Three wasted round trips, every connection, forever.

↑ flip the ndots value

So why did nslookup look healthy? Because it doesn't go through the libc resolver the way curl does — it queries the nameserver with the name you handed it. It was never exercising the search path at all. The tool I was using to validate the fix was bypassing the thing that was broken.

The correction is ndots:1, set via dnsConfig on the application pod:

spec:
  dnsPolicy: ClusterFirst
  dnsConfig:
    options:
      - name: ndots
        value: "1"
      - name: single-request-reopen
06 — The quiet one

Resolution worked. It just took five seconds.

With ndots:1 in place the right query went out first — but some lookups still sat there for what felt like an eternity. Timing one made the shape obvious:

$ time nslookup vendor-api.example.net
Address: 10.20.30.40

real    0m5.02s   # a five-second wall, not a slow server

Five seconds isn't slowness. Five seconds is a timeout — it's glibc's default RES_TIMEOUT, waiting out a reply that never came before retrying. Something was being sent and not answered.

Here's the mechanism. When an application resolves a hostname, glibc doesn't send one query — it sends two, an A record lookup for IPv4 and an AAAA for IPv6, fired in parallel from the same source port. It then waits for two replies on that one socket.

That works fine against a single DNS server. It breaks against load-balanced or NAT'd resolver paths, where the two replies can come back out of order or from a different source address than glibc expects. glibc discards the reply it can't match, waits the full five seconds for the one it thinks is missing, then retries. You get the correct answer — just five seconds late, on every fresh lookup.

The fix is one more line in the same dnsConfig block, and it's the reason both options appear together in the final pod spec:

spec:
  dnsPolicy: ClusterFirst
  dnsConfig:
    options:
      - name: ndots
        value: "1"
      - name: single-request-reopen   # <- this one

single-request-reopen tells glibc to close the socket and open a new one before sending the AAAA query. Each lookup then gets its own source port, the replies can't be confused for one another, and nothing is left waiting on a response that was never coming.

$ time nslookup vendor-api.example.net
Address: 10.20.30.40

real    0m0.01s   # the wall is gone

Two similar options, one right answer

Don't confuse it with single-request, which sends A and AAAA sequentially — that also avoids the collision, but doubles your round trips on every single lookup forever. single-request-reopen keeps the queries parallel and just gives the second one a fresh socket. Same fix, none of the latency tax.

Worth knowing generally

This is a one-line option that quietly resolves a whole class of "DNS is slow" tickets that normally get blamed on CoreDNS capacity — and answered by scaling CoreDNS, which changes nothing, because the five seconds was never being spent on the server side.

07 — The fix

Four settings, and any three of them leave you broken

This is the part that matters in a production environment — not because the individual settings are clever, but because each one fails differently and the failures look nothing alike.

CoreDNShosts entry
Without it, the VIP mapping doesn't exist anywhere in the cluster.
CoreDNS256Mi memory limit
Without it, loading the plugin OOMKills CoreDNS and takes cluster DNS with it.
Application poddnsPolicy: ClusterFirst
Without it, the pod queries node DNS, which has never heard of the VIP.
Application podndots: 1
Without it, the query burns three search-domain lookups first and curl times out.
Application podsingle-request-reopen
Without it, resolution works but pays a five-second AAAA timeout on every fresh lookup.

Note where they live. Three of the five are on the application pod, not on CoreDNS. dnsPolicy and dnsConfig are pod-spec fields; they have nothing to do with the DNS server's own configuration. I lost time chasing this on the wrong side of that boundary.

dnsPolicy is not a free toggle

Worth pausing on, because most write-ups treat this as a one-word switch. Default is badly named — it is not the default, and it means "inherit the node's /etc/resolv.conf and bypass cluster DNS entirely." So moving a workload to ClusterFirst doesn't just reroute the one hostname you're fixing. It swaps the resolvers and the search domain list underneath every name that application resolves.

Pods on Default inherit whatever search suffixes the node carries — often corporate ones. Those vanish on ClusterFirst. CoreDNS forwarding to /etc/resolv.conf gives you the same upstream servers, but it does not hand the pod the node's search list. If anything in that app resolves a short name that only worked because of a node search domain, it stops working the moment you flip the policy — and it'll look like an unrelated outage.

Diff them before you switch. Node /etc/resolv.conf against what a ClusterFirst pod actually gets. Anything in the node's search list that matters goes into dnsConfig.searches, or you go find the short names in the app config first.

08 — The final state

Everything that changed, in one place

The complete CoreDNS Corefile, with the override in position between kubernetes and forward:

.:53 {
    errors
    health {
        lameduck 10s
    }
    ready
    kubernetes cluster.local in-addr.arpa ip6.arpa {
        pods insecure
        fallthrough in-addr.arpa ip6.arpa
        ttl 30
    }
    prometheus 0.0.0.0:9153
    hosts {
        10.20.30.40 vendor-api.example.net
        fallthrough
    }
    forward . /etc/resolv.conf
    cache 30
    loop
    reload
    loadbalance
}

The CoreDNS deployment resources, with the headroom that was missing:

resources:
  limits:
    memory: 256Mi
  requests:
    memory: 128Mi

And the application pod spec — all three DNS settings together, in the chart template rather than patched onto a live deployment, so every pod gets them on every deploy:

spec:
  template:
    spec:
      dnsPolicy: ClusterFirst
      dnsConfig:
        options:
          - name: ndots
            value: "1"
          - name: single-request-reopen

One thing worth saying out loud

Put the pod settings in the chart, not in a kubectl patch. A patched deployment is correct until the next release overwrites it, and then you're debugging the same five-second timeout six weeks later with no memory of why it ever worked.

"Can't this just be cluster-wide?"

Reasonable question, given chapter 02 argued against per-pod configuration. The distinction is that hostAliases forces every team to carry the VIP itself — environment-specific data that goes stale — while dnsConfig is a behavioural setting with no such data in it. Still, the instinct is right.

There's no supported cluster-wide ndots setting. kubelet hardcodes ndots:5 when it builds resolv.conf for ClusterFirst pods, and it isn't exposed as a flag. PodPreset would have been the native answer; it was removed in 1.20. That leaves kubelet's --resolv-conf, which merges options from a file on the node — a bootstrap-level change, invisible to anyone reading your manifests — or a mutating admission webhook, which is what this becomes when it stops being one application and starts being a platform default:

# Kyverno — scope by namespace label, not cluster-wide
mutate:
  patchStrategicMerge:
    spec:
      dnsConfig:
        options:
          - name: ndots
            value: "1"

Cluster-wide enforcement, per-workload intent. That's the combination you actually want, and it's where this goes if a second application ever needs the same treatment.

09 — The morning it worked

Every check, green

CoreDNS came up on 256Mi with the hosts block loaded — both pods Running and Ready, no restarts. The application chart deployed. And then, from inside a real application pod:

$ cat /etc/resolv.conf
nameserver 10.43.0.10          # CoreDNS. not node DNS.
search my-namespace.svc.cluster.local svc.cluster.local cluster.local
options ndots:1              # the override is live

$ nslookup vendor-api.example.net
Address: 10.20.30.40

$ curl -v https://vendor-api.example.net
* Connected to vendor-api.example.net (10.20.30.40) port 443
< HTTP/1.1 200 OK

No trailing dot. First try. Instant.

The application team ran a live transaction end to end and confirmed it landed on the correct load balancer. Nothing else in the cluster lost DNS — internal service discovery kept working exactly as before, which is what fallthrough was there to guarantee.

The quiet win

The best part isn't the fix. It's that it lives in version control now — the Corefile, the memory limit, and the pod spec all reviewed, deployable, and survivable across a cluster rebuild. What started as a hostname somebody wanted redirected ended up as a supported platform capability. That's the difference between solving a ticket and building something.

What I'd tell myself on day one

  • ndots:5 is a cluster-internal optimisation. For workloads that mostly talk outward, ndots:1 or 2 is usually the correct setting.
  • nslookup and dig are not the resolver. Reproduce with the tool the application actually uses, or you will validate a fix that doesn't exist.
  • Read /etc/resolv.conf inside the pod first. Nameserver, search list and options in one shot — it would have cut a day off this.
  • fallthrough in the hosts plugin is mandatory, not stylistic.
  • CoreDNS default memory limits assume the default Corefile. Adding plugins is adding load.
  • A trailing dot is a free diagnostic. If host. works and host doesn't, it's search-domain behaviour. Every time.
  • Change one variable per apply. Memory first, verified; then the plugin. Two changes in one apply means no signal when it breaks.
  • A five-second DNS delay is a timeout, not a slow server. Reach for single-request-reopen before you scale CoreDNS.
  • Put pod DNS settings in the chart, not a live patch. A patched deployment is correct only until the next release overwrites it.
  • dnsPolicy: Default is not the default. Switching off it changes resolution for every name the workload uses, not just the one you're fixing.

None of this is exotic — it's all in the documentation. But it's spread across four different documents, and the failure presents as "curl is broken," which points you in almost exactly the wrong direction. If this post saves someone the two days it cost me, it was worth writing down.
